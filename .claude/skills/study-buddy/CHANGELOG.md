# Changelog

study-buddy的版本记录。版本号规则：主版本.次版本.修订号。

## [3.12.0] - 2026-11-09

### 新增

- 支持macOS和Linux：之前四个脚本里有三个直接依赖Windows的Office COM（`pywin32`），Mac用户装上后资料整理的第一步（PPT、DOC转PDF）就会失败。现在按平台选工具，Windows上的默认行为不变
  - 新增`scripts/office_compat.py`，`ocr_cli.py`和`convert_submission.py`共用：Windows先用Office COM，没装Office、没装`pywin32`或COM出错时自动退到LibreOffice（`soffice --headless`）；macOS、Linux直接用LibreOffice。两者都没有时报环境错误并给出对应平台的安装命令，也可以让用户手动另存为PDF
  - `build_pptx.py`：Windows优先PowerPoint COM，没有PowerPoint或COM出错时退到`python-pptx`；macOS、Linux直接用`python-pptx`。版式和COM版一致（标题和内容，有图时正文占左侧45%、图在右侧，备注写进备注栏），页面用16:9。成功提示末尾会写明用的是PowerPoint还是python-pptx
  - `compile_tex.py`：编译时把模板里的`fontset=windows`换成当前平台的ctex字体集（Windows是`windows`，macOS是`mac`，Linux是`fandol`），tex源文件和模板不用改；macOS上还会到`/Library/TeX/texbin`等位置找`xelatex`；找不到时的安装建议按平台给（MiKTeX、MacTeX、TeX Live）。输出JSON新增`fontset`字段
  - 依赖：`python-pptx==1.0.2`从“可选”改为推荐安装（没有PowerPoint时靠它生成pptx）；macOS、Linux不装`pywin32`（只有Windows能装）。`setup.md`分平台写了安装命令、验证命令和常见问题，README、官网、`introduction.md`、`qa.md`和相关工作流的“依赖Windows和Office”表述同步改掉

### 需要知道的

- 在Windows开发机上测过：LibreOffice转PDF（含中文路径）、Office COM失败时回退LibreOffice、两者都没有时的报错、`python-pptx`生成的pptx（含图片和备注）用LibreOffice渲染检查版式、四个脚本在Windows上的默认路径不变（`build_pptx.py`仍用PowerPoint，`compile_tex.py`仍用`windows`字体集）
- **没有在真实的macOS或Linux上跑过**：Mac路径只做了逻辑和命令层面的模拟（`soffice`在`/Applications/LibreOffice.app`下的查找、`mac`字体集、`/Library/TeX/texbin`查找），安装命令（`brew install --cask libreoffice mactex-no-gui`等）也没有实测。Mac用户遇到问题请反馈
- LibreOffice转出的PDF与Office版式有细微差别（特殊字体、艺术字），OCR取字不受影响；对提交PDF的版式有严格要求时，建议在装了Word的电脑上导出
- `python-pptx`版的pptx使用它自带的默认模板，外观比PowerPoint默认主题朴素一些，用户本来就要在PowerPoint里调样式，不影响使用
- 不同平台的中文字体不同，同一份小抄在各平台编译出的页数可能略有差别，限页数时以当前平台的编译结果为准
- 没有`pywin32`的Windows环境也能用了：转PDF退到LibreOffice，生成pptx退到`python-pptx`

### 迁移

- 不需要迁移。Windows用户行为不变；想在没有Office的电脑上用，装LibreOffice和`python-pptx`即可

## [3.11.1] - 2026-11-08

### 变更

- 更新提示里直接带上更新内容：原来`check_update.py`只返回版本号和一个Release页链接，助手拿不到内容，只能更新完再去读本地`CHANGELOG.md`。主版本升级时按规则要“先告诉用户更新内容、同意后再更新”，那时还没更新，助手没有内容可讲，这是个缺口。现在发现新版本时，提示里附上“本地版本之后到最新版本之间所有版本”的CHANGELOG段落（新的在前），跳过了几个版本的用户也能看全
  - 按最新版本的tag从`raw.githubusercontent.com`取`CHANGELOG.md`，和发布出去的版本一致，不会读到`main`上还没发布的改动
  - 只在发现新版本时才多请求一次，按版本缓存；取失败也缓存6小时，避免每个脚本结束都多等2秒。取不到时提示和以前一样，只有链接，不影响使用
  - 提示里最多放约6000字，超出截断并指回链接，避免落后很多个版本时刷屏
  - `SKILL.md`的自动更新规则同步：主版本升级时用提示里的内容跟用户说；更新后优先用提示里附的，没有再读本地`CHANGELOG.md`；要求讲重点，不整段照搬
  - 网络访问多了一个域名：`raw.githubusercontent.com`，只读，`setup.md`的“网络与权限”已写明

### 需要知道的

- 用真实网络测过：从v3.9.0落后到v3.11.0，提示里带出了3.10.0和3.11.0两段；只落后一版只带最新一段；主版本升级仍标“自动更新：否”；CHANGELOG取不到或tag不存在时退回只有链接；缓存命中不再联网。截断逻辑用构造的超长数据测过
- 3.11.0本身发布时还没有这个功能，所以从3.11.0更新到3.11.1时，提示里仍是旧格式（只有链接）；3.11.1之后的版本才会带更新内容

## [3.11.0] - 2026-11-08

### 新增

- 每门课可以单独设目标：保过（默认）或高分（目标分N）。有用户反馈不只想过及格线，还想冲高分，原来的定位只限制排期和取舍，没有限制单项任务做到什么程度，所以不改产品的主承诺，把目标做成每门课的参数
  - 目标写在该课`课程信息.md`的“基本信息”里。建课时问一次，用户没想好就写保过，不追问；学期中随时可以改，用户说“这门我想冲90”或“这门保过就行”，只改这一门课的文件，再更新`学期规划.md`里这门课的行。没有“目标”栏的旧`课程信息.md`按保过处理
  - 用户只说“尽量高”没给数字时，问一个具体分数；仍然不给就按保过安排，并说明高分需要的时间没法估
  - 差距按目标线算（保过课是及格线，高分课是目标分）。高分课的预期得分率不再默认60%，按用户已出分的成绩或自己的判断估，没有依据就问，仍没有按70%暂估并标“暂估”
  - 学期规划：所有课先排到保过线，剩余时间再按“每多花1小时能多拿几分”分给高分课，高分课的冲刺投入排在所有课的保过任务之后，不会为了冲高分挤掉别的课的保过。保过所需小时和高分额外投入小时分开列；目标分和可用时间对不上时，如实说差多少、缺多少小时（标估算），由用户决定降目标、减别的课的投入还是接受风险
  - 高分课不建议放弃任何考核；作业、论文、pre按评分标准的最高档去做
  - 期末速通：高分课在原有做法之外，低权重的“半会”“不会”点也要过，往年题限时做并按失分原因分类，同一点错两次以上回到带学重讲，另给一份“最容易丢分的点”清单（来源是用户的错题本），至少两套限时模拟，预估分数低于目标线时如实说。不到1天时高分课和保过课没有区别
  - 触发：`SKILL.md`的description和路由加了“这门课想冲90”这类说法，进学期规划
  - 总览`学期规划.md`的课程清单新增“目标”“目标线”两列，原来的“及格线”列并入“目标线”

### 变更

- `references/pass-strategy.md`改名为`references/score-strategy.md`，内容改写为目标、差距计算、保过方案和高分方案；所有指向它的链接已同步。文件内容里的“最低投入方案”改称“保过方案”
- README、官网和`introduction.md`的主承诺仍是“每门课及格”，只加了一句“想冲高分的课可以单独设目标分”

### 需要知道的

- 高分方案里的几个数没有依据，是经验做法：高分课预期得分率暂估70%、额外投入小时靠最低小时数表估算、“每多花1小时能多拿几分”的排序也是定性判断，没有按真实用户校准过。用一两个学期后应该按实际完成情况修正
- 没有真实用户跑过高分课的完整流程；示例`course-info_example.md`里的高分路径数字是手算的，用来示范写法

### 迁移

- 不需要迁移。已有的`课程信息.md`没有“目标”栏时按保过处理；已有的`学期规划.md`课程清单是旧的列（及格线），下次更新时按新模板改成“目标”“目标线”两列

## [3.10.0] - 2026-11-06

### 新增

- 第三个OCR引擎：MinerU，同时支持OXR商业版key。paddle、oxr、mineru是三家不同的供应商，key互不通用。引擎的选择和失败退路用同一条优先级链：**paddle key → oxr key → mineru key → oxr免费接口 → mineru免登录轻量接口**。没填key的档位跳过（oxr免费接口、mineru轻量接口不需要key，永远在链里）；默认引擎paddle没填key时（原来直接退用OXR免费接口），从链上第一个可用的档位开始；运行中某一档失败，依次退到后面的档位，每次退用都记在摘要的`warnings`里。`config.json`的`engine`写`oxr`或`mineru`，或命令行加`--engine`，是从该家在链里最靠前的可用档位开始；token填在`mineru.api_key`（模板里的示例值`MinerU_API_KEY`保留时视为没填，和`sk-123`、`paddle-token-123`一样）
  - 退路改变：原来Paddle额度用完（HTTP 403）后停止提交后面的块，现在这份资料后面的块会自动退到链上的下一档，也就是资料会上传到另一家供应商；链上所有档位都失败才停止。显式`--engine paddle`又没有key仍然报错退出，不悄悄换引擎
  - OXR商业版：`oxr.api_key`填真实key后改走`oxr.paid_base_url`（默认`https://somark.ai/api/v1`），请求方式和免费接口相同，key作为`api_key`表单字段提交；模板示例值改为`OXR_API_KEY`，旧版的`dummy`同样视为没填。商业版的切块上限沿用免费版的20页、10MB，没有用真实key验证过
  - 各档的单块上限不同，退到下一档时按那一档的上限把块重新拆开再拼回，页号和原来的块对齐
  - 填了token：走精准解析接口，`vlm`模型，有分页、公式、表格和图片文件
  - 没填token：走免登录的Agent轻量接口，`pipeline`模型，按IP限频。限制：每块最多20页、10MB（切块上限自动收紧到这个值），只返回一份Markdown，没有分页信息，所以整块内容放在块的第一页，草稿里标注“第N–M页的合并输出”，出处页码只能标到块级；也没有表格和公式识别。排队时间不可控，等待上限单独设为120秒（`mineru.agent_job_timeout_seconds`），超过按失败处理。它是优先级链的最后一档，没有后续档位可退，这一块标记失败，重跑可补
  - 失败退路：key无效或过期、额度用尽、排队超时属于“后面的块多半也一样”，这份资料后面的块都从下一档开始；其他错误只让当前这一块退到下一档。每次退用都记在摘要的`warnings`里，写明哪一档因为什么失败、改用了哪一档
  - 流程仍是Office转PDF、按页切块、逐块上传，只是上传、轮询、取结果换成MinerU的批量上传接口：申请上传链接、PUT上传、轮询、下载结果包。结果包里的`content_list.json`按页转成与其他引擎一致的结构，所以后面的草稿组装、页码标记、图片转写都不用改
  - 图片随结果包一起下来，不是外链，链接过期的问题不存在：图片存在课程文件夹的`.缓存/<资料序号>/<块>_img/`，“下载”阶段改为复制并校验，进度行里的图片n/total照常显示。缓存里的图被删了会走原有的单页补OCR
  - 页数以块PDF的真实页数为准，没有内容的页也返回一个空页，保证页码和切块一一对应；结果里的页数和切块页数对不上时按失败处理
  - 类型处理：正文、标题、公式（`equation`，LaTeX）、列表、代码、图片、图表（`chart`，和图片一样当图片处理）、表格（HTML正文，没有正文时退回表格截图交给VLM）；页眉、页脚、侧边文字不进正文，页码存成页码标记；不认识的类型只要有文字就保留，宁可多不能漏
  - 错误分类：token错误（A0202）、token过期（A0211）、每日任务数用尽（-60018）、HTTP 401和403按致命错误处理，停止提交后面的块；限流（429）等待后重试；其余错误重试，仍失败的块标记失败，重新运行只重做失败的块
  - 速度：实测有波动，单个任务不排队时63页约1分半，同时提交多个任务时排队可达数分钟，所以`job_timeout_seconds`默认1800秒。`--dry-run`按每分钟20到60页估算，只作参考
  - 配置项：`mineru.base_url`、`model_version`（默认`vlm`）、`max_pages_per_chunk`（默认100）、`max_mb_per_chunk`（默认100）、`timeout_seconds`、`poll_seconds`、`job_timeout_seconds`、`retry_429_seconds`；旧版`config.json`没有`mineru`段时在内存里按模板补齐，不改用户的文件

### 需要知道的

- 用一份63页的课件PPT和自造的PDF实测过：直接传PPT、转成PDF再传、表格、公式、页眉页脚、页码、列表、错误token、超过200页、损坏文件。直接传PPT时MinerU在服务端自己转换，会漏掉个别页（实测漏过一页题目），所以走的是我们自己的转PDF再切块，不直接传Office文件
- `page_ranges`参数对PPT不生效，对PDF生效；我们的流程本来就是切好块再传，没有用它
- 没有测过：整本教材规模、真实图表较多的资料对比Paddle的质量、并发限流。质量对比没有做，不要把MinerU当成比Paddle更好的结论，两者的草稿口径也不同
- 免登录轻量接口只用本地模拟服务测过流程（切块上限、整块Markdown拆成文字块和图片块、块级页码标注、图片下载、超时按失败处理，以及各档之间的退路），真实服务没有拿到过结果：在开发机上提交了4个任务（文件上传3个、官方示例PDF的URL提交1个），都提交成功，之后一直处于排队状态，最长的等了30多分钟没有变化，同一时间精准接口几十秒就出结果。不清楚是匿名队列积压、IP被限频还是接口故障，只测了一台机器。所以它的真实表现、排队多久、Markdown里图片是不是可下载的外链、有没有表格公式，都没有验证
- 结果包的下载链接隔几分钟仍可用，有效期没有测

### 迁移

- 不需要迁移。默认引擎仍是`paddle`；没填任何key的用户行为不变，仍是OXR免费接口，只是失败后多了一档MinerU免登录轻量接口可退（页码只有块级范围、没有表格公式识别）。填了`oxr.api_key`或`mineru.api_key`的用户，Paddle没key时会优先用它们。Paddle额度用完后不再停下，会自动退到下一档，资料随之上传到另一家供应商

## [3.9.0] - 2026-11-05

### 新增

- 自动更新：之前只有“检测到新版本，提示用户自己去更新”，没有写助手收到提示后该做什么，用户直接说“更新study-buddy”也没有对应的指令。现在由主skill自己负责保持最新
  - 检查时机：每次对话第一次用到本skill时，助手先运行一次`python scripts/check_update.py`（结果缓存24小时，查不到就静默）；四个脚本结束时的`[更新提示]`同样处理
  - 同一主版本（如3.8.0到3.9.0）：提示里写“自动更新：是”，助手直接运行更新命令，不用问用户。脚本运行中途或正在写某份交付物时不更新，等这一步完成再更新；更新完重新读一遍`SKILL.md`再继续，因为路由和规则可能变了
  - 主版本升级（如3.x到4.0）：提示里写“自动更新：否”。历史上主版本升级都带不兼容的变更（2.0.0、3.0.0），所以先把更新内容告诉用户，用户同意后再更新
  - 用户说“更新study-buddy”时同样处理；更新后读新版本`CHANGELOG.md`最前面一段，用几句话告诉用户更新了什么；`study-buddy-data/`不受影响
  - 更新命令仍按安装位置区分：项目内`npx skills update study-buddy`，全局带`-g`
  - 设置环境变量`STUDY_BUDDY_NO_UPDATE_CHECK=1`会同时关闭检测和自动更新
- `SKILL.md`的description加了“用户说‘更新study-buddy’时也使用”，让这句话能触发加载本skill

### 变更

- `check_update.py`单独运行时把输出设为UTF-8：助手现在会直接运行它读提示，Windows默认按系统代码页输出，中文会乱码

### 需要知道的

- 自动更新要求助手真的去执行`npx skills update`，需要网络和Node.js。没有Node.js、命令失败时只报错误的关键一行，不重试，不影响当前任务
- 更新命令在真实环境里的行为没有验证：`npx skills update`在项目内安装时是否只更新本项目的那一份、更新是否保留用户在skill目录里改过的文件，都没有实测。`check_update.py`的判断和输出用模拟的缓存测过
- 更新会替换整个skill目录。如果用户改过skill里的文件，会被覆盖

### 迁移

- 不需要迁移。已有数据不受影响；旧版本不会自动更新，需要用户手动更新到3.9.0一次，之后才会自动

## [3.8.0] - 2026-11-05

### 新增

- `ocr_cli.py`实时输出进度：之前只有块开始和失败的几行，Paddle提交后轮询最久30分钟一行都不打，整本教材要十几分钟看不出是在跑还是卡住。现在进度行统一带`[进度]`前缀，写到stderr，随时刷新，stdout的JSON摘要不变
  - 每份资料开始、结束：结束行含状态、页数、失败页、图片数（已转写、未转写、下载失败）和用时
  - 每个块完成：已处理页数/总页数和百分比、已用时间，第一块完成后还有预计剩余（按已完成的块外推）；有失败页时一并报
  - OCR等待期间每60秒一行“块2/5仍在处理，已等待3分钟”，补OCR时同样
  - 图片下载：块完成时带上累计下载数，收尾阶段定时报n/total，结束时报成功和失败数
  - 图片转写：开始时报张数、合并后的请求数和并发，之后报n/total，最多打20行左右，图片上百张时不刷屏
  - 全部结束时一行总结
- 断点续传补全：每个块解析完（成功或失败）就立刻保存进度，切块计划生成后也保存一次。之前`manifest.json`要等整份资料处理完才写，进程被强杀（关终端、断电、后台任务被取消）时，已经解析完的块虽然缓存在磁盘上，但没登记，重跑会全部重新OCR，白白消耗额度。现在只丢弃正在进行、还没返回结果的那一块，其余不再重做
  - 保存时先写临时文件再替换，写的过程中被杀也不会留下半截的`manifest.json`
  - 上次已经下载到磁盘、但没来得及登记的图片，重跑时直接认领，不再按旧链接重复下载；下载到一半的残缺文件和空文件会被清掉重新下载
  - 3.6.0里“上次中断留下的缺图块重新运行时先下载，不重新OCR”这句话，之前只在脚本正常结束（如某块失败）时成立，强杀时不成立，现在两种情况都成立
- 助手要主动转告进度：资料整理第3步新增要求。后台运行时，启动后先告知已开始和预计时间，之后每隔几分钟读日志末尾的`[进度]`行，用一两句话转告；失败页、图片下载失败、某份资料结束、进度长时间停在“仍在处理”时要点出来。进度没变化不等于卡住，不要因此中断脚本

## [3.6.0] - 2026-11-03

### 变更

- 图片下载提前并行：OCR引擎返回的图片是临时链接，会过期。之前要等整份资料全部解析完才统一下载，几百页的教材第一块的链接要等十几分钟才被用到。现在每解析完一块就马上下载这一块的图片，和后面块的OCR同时进行

### 从2.0.0迁移旧数据

旧的`学期规划.md`需要拆开，不拆的话新规则找不到各课的`课程信息.md`。对旧`学期规划.md`里登记的每门课，让agent或手工按下面做：

1. 在该课的课程文件夹（如`0501_概率论与数理统计/`）里，按`assets/templates/course-info.template.md`新建`课程信息.md`
2. 从旧文件的“课程清单”表里取这门课的及格线、期末需单独及格、评分构成，填到“基本信息”
3. 把旧文件“各课考核与截止时间”下这门课的考核表原样搬到“考核表”；表末加“已得分”列，数据取自旧课程清单里的“已得成绩”，没出分的写“无”
4. 把旧文件“及格路径”下这门课的小节搬到“及格路径”
5. 全部课搬完后，按新`semester.template.md`重写`学期规划.md`：课程清单改成新列（“还差分数”取自各课及格路径里的“还差”，“信息状态”按完整度填），新增“截止时间”表（汇总各课未完成的考核，按日期从近到远），保留“每周准备清单”，过去的周压成一行
6. 核对：`学期规划.md`里每门课的及格线、还差分数和截止时间，都能在对应的`课程信息.md`里找到一致的值

迁移不涉及`讲义/`、`原始资料/`等其他目录，也不改`manifest.json`。
